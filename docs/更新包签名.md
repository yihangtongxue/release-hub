# 更新包签名接入

ReleaseHub 按产品配置更新包签名策略，适用于任意产品和支持的仓库平台，不根据仓库地址或产品名称启用特殊规则。客户端仍需适配 ReleaseHub 的更新清单协议。

## 产品配置

在新增或编辑产品时设置：

- **签名可选**：允许安装包没有签名文件；存在签名文件时必须完整验证，损坏或无法读取时拒绝发布。新产品默认采用此模式。
- **必须签名**：本次发布的每个安装包都必须有同目录的 `<完整文件名>.sig.json`。
- **应用标识**：签名载荷中的 `appId`，例如 `com.example.desktop`。必须签名时必填；可选模式填写后也会检查一致性，不填写则只验证签名载荷自身的 appId 为非空字符串。

策略适用于该产品本次发布的所有平台和包类型。ReleaseHub 不读取私钥、不生成签名、不请求私钥密码。签名工具由产品自己的构建流程提供。

## 旧产品迁移

数据库迁移 7 增加产品级签名策略与应用标识，已有产品初始为“尚未配置”，不会根据名称或仓库猜测配置，也不会自动放宽签名要求。下一次发布前，打开“编辑产品”选择策略并保存；原本依赖签名更新的产品应选择“必须签名”，填写客户端已使用的 appId。

迁移保留已有发布分支、版本和附件签名。读取历史版本及匿名下载校验不要求先配置策略。配置仅保存在本机，删除后重新添加产品或更换设备时需要按客户端约定重新配置；远端历史不决定本机签名策略。

## 签名文件格式

示意格式（占位值不能直接用于发布）：

```json
{
  "algorithm": "ed25519",
  "keyId": "原始公钥字节的 SHA-256 小写十六进制摘要",
  "publicKey": "32 字节 Ed25519 原始公钥的标准 Base64",
  "payload": "UTF-8 JSON 原始字节的标准 Base64",
  "signature": "对 payload 原始字节签名所得的 64 字节签名的标准 Base64"
}
```

`payload` 解码后的 JSON 必须包含且仅包含以下字段：

```json
{
  "schemaVersion": 1,
  "appId": "com.example.desktop",
  "channel": "stable",
  "version": "1.2.0",
  "platform": "macos",
  "architecture": "arm64",
  "packageType": "zip",
  "fileName": "Example-1.2.0.zip",
  "size": 123456,
  "sha256": "安装包的 SHA-256 小写十六进制摘要"
}
```

在创建远端 Release 之前，先对 payload 原始字节验签，再逐项比较版本、应用标识（如已配置）、渠道、文件名、平台、架构、包类型、大小和哈希。验签不能先解析再重新序列化 JSON。

验证通过后，`algorithm`、`keyId`、`payload`、`signature` 写入 `assets[].updateSignature`，不会写入 `publicKey`。全部附件上传成功后才更新 stable.json。数据库迁移 6 保存历史附件的可选签名字段，未签名的旧版本仍可读取。

## 客户端信任约定

签名文件中的公钥只能证明签名文件与载荷自洽，应用标识匹配也不能证明发布者身份。客户端必须使用内置或通过可信渠道配置的公钥验签，不得信任更新清单提供的任意公钥。发布后的“校验客户端下载”仅检查匿名下载、文件大小和 SHA-256，不代替客户端验签及实际升级验收。

发布时选择原安装包，勿将 `.sig.json` 作为构建产物上传。移动安装包时同时移动签名文件；改名、改版本、改目标或重压缩后需要重新签名。

## 待人工验收

以下项目尚未运行验证：

- 两个任意产品使用不同 appId，在 GitHub/Gitee 上独立配置与发布。
- 可选模式无签名可以发布；有正确签名则透传；损坏签名不能忽略。
- 必须签名时，缺少文件、错误 appId、错误版本/目标/大小/哈希均在远端变更前失败。
- 可选模式填写 appId 后，也拒绝其他应用的签名。
- 旧产品迁移后首次发布提示配置，保存和重启后回显正确，原分支及历史保持不变。
- 发布或校验期间不能修改产品配置。
- 客户端按原始 payload 字节及内置信任公钥验签，完成真实升级。
